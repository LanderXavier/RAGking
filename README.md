# RAGking v2.1

## Lightweight Multidimensional Evaluation Framework for RAG Pipelines

RAGking is an automated evaluation framework designed to assess the quality, efficiency, operational cost, and robustness of Retrieval-Augmented Generation (RAG) systems. The framework provides a reproducible and interpretable score that combines factual correctness, economic efficiency, latency, maintenance burden, and failure rate into a single composite metric.

This repository implements a research-oriented evaluation pipeline for benchmarking RAG systems on structured question-answering datasets. It is intended for experimental reproducibility, model comparison, and systematic operational auditing of retrieval-augmented generation workflows.

---

## 1. Project Description

The project evaluates RAG pipelines under a multidimensional perspective rather than relying on a single benchmark metric. In many production scenarios, a model may appear acceptable in terms of answer quality while being inefficient, expensive, or difficult to maintain. RAGking addresses this problem by combining:

- factual correctness via LLM-as-a-Judge,
- semantic alignment via embedding similarity,
- token and cost efficiency,
- end-to-end latency,
- maintenance burden,
- failure rates.

The resulting score is normalized to a 0–100 scale and can be weighted according to the application domain. This makes it suitable for research, system comparison, and deployment planning.

### Main objective

To provide a transparent and reproducible evaluation framework for comparing alternative RAG orchestration strategies or models under identical experimental conditions.

## 2. Dataset Information

The framework expects a tabular dataset in CSV format containing question-answer pairs and execution metadata. Each row represents one evaluation sample.

### Required columns

The core workflow assumes the following fields:

- Question
- Correct Answer
- Generated Answer
- Prompt Tokens
- Completion Tokens
- Total Tokens
- Execution Time (ms)

### Optional columns

These improve the operational and comparative analysis:

- Model
- is_failure
- failure_rate
- deploy_hours
- implementation_difficulty
- maintenance_hours_week

### Dataset assumptions

The framework is designed for benchmark-style evaluation where each sample includes:

1. the user question,
2. the ground-truth answer,
3. the answer generated by the RAG system,
4. the number of prompt/completion tokens used,
5. execution latency,
6. model or pipeline metadata for comparison.

The framework can operate on custom datasets, public QA benchmarks, or internally generated evaluation corpora. It is especially useful for evaluating tasks that require factual retrieval and answer grounding.

- LLM-based correctness evaluation,
- embedding similarity estimation,
- operational cost and maintenance calculations,
- normalization and bound extraction,
- composite ranking score,

## 4. Framework Methodology

The methodology follows a reproducible pipeline composed of several stages.

### 4.1 Data ingestion

The framework loads a CSV file with evaluation examples. The input columns are validated and the dataset is transformed into a pandas DataFrame for downstream processing.

### 4.2 Correctness assessment

For each question-answer pair, the system compares the generated answer against the correct answer using an LLM judge. The judge scores factual correctness on a discrete scale from 1 to 5:

- 1: no relevant or correct information,
- 2: major factual errors,
- 3: partially correct,
- 4: mostly correct,
- 5: highly accurate and faithful.

This process is implemented in core/llm.py and follows a prompt-driven factual evaluation strategy.

### 4.3 Semantic similarity

In addition to correctness, the framework computes embedding-based semantic similarity using cosine similarity. This complements the judge score by measuring the semantic closeness between the correct answer and the generated answer.

### 4.4 Operational metrics

The framework also quantifies operational factors such as:

- total token usage,
- cost per query,
- execution latency,
- deployment and maintenance burden.

These are used to estimate the maintenance score and to assess economic feasibility and deployment sustainability.

### 4.5 Normalization and bounds

Each metric is normalized to a common scale so the model can combine heterogeneous variables. The code supports both min-max normalization and bound-aware normalization using saved metric ranges.

### 4.6 Composite score

The final RAGking score combines normalized dimensions using configurable weights:

$$
RAGking\ Score = (w_C \cdot \hat{C} + w_E \cdot \hat{E} + w_L \cdot \hat{L} + w_M \cdot \hat{M} + w_F \cdot \hat{F}) \times 100
$$

where:

- $\hat{C}$: correctness,
- $\hat{E}$: economic efficiency,
- $\hat{L}$: latency,
- $\hat{M}$: maintenance,
- $\hat{F}$: failure rate,
- $w$: domain-dependent weights.

The default configuration uses the following weights:

- Correctness: 0.30
- Economic Efficiency: 0.30
- Latency: 0.20
- Maintenance: 0.10
- Failure: 0.10

This weighting reflects the importance of answer accuracy while still accounting for resource efficiency and system reliability.

## 5. Evaluation Metrics

The framework computes several key metrics for each query and then aggregates them into a single model-level score.

### Correctness

A factual evaluation score assigned by the judge model.

### Economic Efficiency

A cost-aware metric that relates answer quality to token cost:

$$
Economic\ Efficiency = \frac{Correctness}{Cost_{query}}
$$

### Latency

Measured as execution time in milliseconds and normalized so lower latency is preferred.

### Maintenance

Estimated from operational burden indicators such as deployment time, implementation difficulty, and maintenance effort per week.

### Failure Rate

A normalized failure score computed from rows where the model produced no valid answer or the input is marked as failed.

### 6. Use the interactive menu

The CLI follows a sequential two-stage workflow that is important to understand before running evaluations:

#### Stage 1: Load the dataset and generate raw metrics

This is the first analysis pass. The user loads a CSV dataset and then executes the raw metrics routine. In this step, the framework computes the quality and operational signals required to understand the distribution of the data and its current bounds.

This stage includes:

- loading the evaluation dataset,
- checking required columns,
- computing Correctness using the LLM judge (1–5 scale),
- computing embedding similarity,
- estimating token cost and latency,
- deriving failure indicators,
- saving a bounds profile for the current dataset.

This step is essential because it reveals the dataset's empirical range and behavior before normalization. It is not the final ranking stage; it is the descriptive and calibration phase.

#### Stage 2: Generate the normalized report and compare runs

Once the raw metrics are available, the user generates the report from the raw metrics/bounds. In this second stage, the framework normalizes the variables to a common scale and calculates the final RAGking score.

This stage is where the final visualizations and ranking are produced. The important concept is that the comparison is performed on the already computed results from one or more evaluation runs, not on the raw dataset alone.

The practical workflow is:

1. Load CSV.
2. Generate raw metrics and save bounds.
3. Use the raw metrics (or saved exported CSV) to generate the normalized report.
4. Compare two or more evaluation results from the same dataset or from equivalent QA test sets.
5. Visualize the final ranking, score distributions, and operational trade-offs.

This design is especially useful when evaluating different orchestration strategies, for example:

- same dataset, different RAG prompting pipelines,
- same benchmark, different retrieval strategies,
- same QA benchmark with generalized or domain-specific knowledge bases,
- multiple models or orchestration frameworks under the same evaluation protocol.

This mirrors the intended long-term use case: researchers and practitioners can benchmark the same dataset under different RAG configurations and compare them fairly using a common measurement protocol.

## 8. Reproducibility Guidelines

To ensure reproducible experiments:

1. Fix the model versions and API endpoints used in the evaluation.
2. Store the dataset version and preprocessing steps.
3. Save the bounds profile generated by the framework.
4. Record the weight configuration used in the aggregate score.
5. Keep the same prompt template and temperature for the judge model.
6. Export metrics, plots, and reports from the same execution environment.

The project stores normalization bounds in bounds.json and allows scores to be reproduced via consistent repeated runs.

## 10. Example Workflow

A standard reproduction workflow is:

```bash
python main.py
# 1) Load dataset
# 2) Configure LLM providers and models
# 3) Generate raw metrics and bounds
# 4) Produce final score report
# 5) Export charts and summary files
```

This workflow ensures that all critical evaluation steps are grounded in the same data and configuration settings.

### Recommended long-term evaluation protocol

The strongest use case for this framework is to compare RAG systems under a controlled evaluation protocol. In future experiments, the most valuable scenario is to evaluate:

- the same QA dataset with different orchestration strategies,
- the same retrieval pipeline with different generators or models,
- a generalized QA dataset together with domain-specific augmented data,
- multiple framework implementations under identical metrics and weights.

This makes it possible to isolate whether improvements come from the retrieval layer, the generation model, the knowledge source, or the orchestration design itself.
